# xmip-core-transport-aws-s3

Amazon S3 transport: Signature Version 4 over the REST API — list a prefix, get each object and delete it once the runtime accepts it, put a Stream as an object — a bucket prefix is a Location. A technology of [xmip-core-transport](https://github.com/IlleNilsson/xmip-core-transport).

Both ends sign and verify with one signer (`client::signer`): the `s3`
scope, built `hashing_payload_in_header`, so the payload hash travels in
`x-amz-content-sha256` as S3 asks.

Signature Version 4 comes from [xmip-core-transport-aws](https://github.com/IlleNilsson/xmip-core-transport-aws), where every AWS technology shares what AWS speaks over HTTP (ADR-0044, amendment 2026-09-24); HTTP itself comes from [xmip-core-transport-http](https://github.com/IlleNilsson/xmip-core-transport-http).

A Location signs as the access key ID its `access_key_id` setting names, with the secret access key its `secret` holds: a `password` secret kept in the Administration Database and never in configuration, read at each request — a put, a listing, a claim, a get, a delete — so one set or replaced reaches the next request without a restart (ADR-0019, amendment 2026-10-29; ADR-0015, amendment 2026-11-25). A Location naming a secret and no `access_key_id` is refused as the node starts: Signature Version 4 names the access key ID with every signature (`aws::access_key`).

Requests go on connections kept between them (`http::endpoint::Connections`, offering HTTP/1.1): the transport holds them and hands them to every client it makes, so a call costs one exchange and not a connect, a TLS handshake and a `Connection: close`, as it did until 2026-09-27.

## One node receives an object

Several nodes may list one bucket; each object is received by one of them (ADR-0024, amendment 2026-11-20). A receive claims each object it hands over by putting `<key>.xmip-claim` beside it with `If-None-Match: *` (`Client::put_new`), which S3 stores only where no object of that key exists and answers `412 Precondition Failed` otherwise — "the first write operation to finish succeeds" ([*conditional writes*](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)). The claim holds the claimed name the file family records, the key, the node's location, which start of it claimed and the time in nanoseconds; an object whose claim is listed is passed over without a request, and one whose put S3 refuses is passed over. The sequence is the capability's, written once (`transport::listed::Claims`); this crate implements only the bucket's calls (`bucket::Bucket`, `transport::listed::Store`). The claim is deleted with `If-Match` its own `ETag` however the cycle ends — after the object on Accepted, alone on Refused and Failed — and one S3 does not answer is deleted at the next listing. A node that starts again (`Configured::on_node`) reads each claim listed at its first receive that reaches S3 and deletes every one an earlier start of the node holds, never one of its own start, whichever of its Locations made it, so a Location built while another of the same start receives over the same prefix leaves what that one holds (ADR-0024, amendment 2026-11-22); another node's claim is left whatever its age, so a node gone for good leaves its objects claimed and in place. Per object the claim costs one conditional `PUT` at the listing and one `DELETE` at its verdict, and the Location's credentials need `s3:PutObject` for it. `Transport::claims` answers the same claim for one object by its address. On an S3-compatible endpoint that ignores `If-None-Match: *` every claim's put succeeds, so two nodes may both receive one object there: twice, never lost (open problem 75).

## How a received object is acknowledged

A receive deletes nothing and gets nothing: it lists the prefix, and each object's `GET` is made when the runtime first reads its body (`transport::listed::Claims::listed`, the capability's one object-store receive, over `transport::body::fetched`), whole (`net::http` reads a response body whole), so a receive that lists a hundred objects holds none of them in memory. Every object stays in the bucket until the runtime gives its verdict after the whole receive cycle (runtime-model section 5). Accepted deletes the object. Refused leaves it where it lies — a refusal is not a consumption, and a Stream refused at a transport gate was never written to the Ledger, so the object is the only copy — and this Location does not receive it again while its `ETag` is unchanged (`transport::Refused`, which the listing is sifted through: the client lists each key with its `ETag`, read by the capability's one listing scan, `transport::listed::Listing`); one written again under its key has another `ETag` and is a new arrival. The memory is the node process's: a node started again receives a refused object once more, refuses it once more, and remembers it from then on. Failed leaves it, and the next receive lists and gets it again. Until 2026-10-02 a receive got every object it listed before handing any on. A crash before the verdict leaves it too, claimed until its node starts again: at-least-once, never a loss. The delete is the one the receive made until 2026-10-02, so a verdict adds no request but its claim's delete.

The get and the delete hold to the `ETag` the listing gave, in `If-Match` (`Client::get_as_listed`, `Client::delete_as_listed`; ADR-0024, amendment 2026-11-19), for no extra request. An object written again between its listing and its first read is not read under the old `ETag`: S3 answers `412`, the read fails, the cycle fails, nothing is deleted, and the next listing takes what lies there now as a new arrival. An object written again between its read and its acceptance is not deleted: S3 answers `412`, and what was accepted is done with while the replacement stays for the next listing. S3 answers `404` where the object was deleted since and, for a delete, `409` where a `PUT` or `DELETE` completed while it was being judged; each is the same "changed", read from the status before the answer is judged. General purpose buckets take `If-Match` on `DELETE` since 2025-09-16, and it asks for `s3:GetObject` beside `s3:DeleteObject`. Sources: AWS, [*GetObject*](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html), [*DeleteObject*](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html), [*How to perform conditional deletes*](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-deletes.html), [*Amazon S3 now supports conditional deletes in S3 general purpose buckets*](https://aws.amazon.com/about-aws/whats-new/2025/09/amazon-s3-conditional-deletes-s3-general-purpose-buckets).

`Client::put_new` is a receive's claim and the archive's put: `PUT` with `If-None-Match: *`, which S3 answers `412` where an object is there already, writing nothing over it, and otherwise the `ETag` it stored, which it hands back; a `409 ConditionalRequestConflict` is retried once, as AWS says ([*PutObject*](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). A Send Location's put, `Client::put`, writes over what is there, as S3 does.

A send target is read by `net::Target` in [xmip-core-library-net](https://github.com/IlleNilsson/xmip-core-library-net), the one reading of a URI every technology calls: scheme, authority, path and decoded query. Until 2026-09-28 it was read through the transport capability's `socket::target`, which split it on its first slash and left the query in the path.

## The declaration

What a Location of this technology is configured with is two `const`s in its `declaration` module, `src/declaration.rs`, beside the code, which `Configured` reads (ADR-0064, amendment 2026-11-26): `declaration::SETTINGS`, `region`, `access_key_id`, `bucket`, `prefix` and `timeout`, and `SCHEMES`, `aws-s3`; `access_key_id` is the AWS crate's, which this crate's declaration takes by that crate's own `declaration` feature. Built with its `declaration` feature alone (`--no-default-features --features declaration`), the crate is those and nothing more: its code and every crate the code is built on — the http technology, and with it TLS — are behind the default feature, and `tls`, which is code, turns the default on with it. So the library the surfaces load carries it without the code, through the gathering crate xmip-core-declaration (open problem 48), and the language server and the desktop suggest and check an aws-s3 Location's settings, its `access_key_id` among them, though no node in their process loaded the technology. `test/Declaration.Test.ps1` in the estate holds that the declaration builds nothing the transport capability does not.
